# Живая приёмка MVP-01.05, выпуск 78273fc

Проверка 2 ноября 2026 года. Сотруднику нужна стабильная панель внутри amoCRM,
которая согласует учёт времени с задачами и не теряет работу при навигации.
Этот документ фиксирует наблюдения установленного выпуска. Полная приёмка
остаётся открытой из-за воспроизводимого дефекта настроек и непроверенной роли.

В `amotehrkrs` использованы тестовая сделка `39246629` и контакт `42417583`.
Созданы две выделенные задачи с префиксом «МВП-01.05 live 78273fc».
Одна завершена штатной кнопкой amoCRM, другая через панель. Обе сохранили
переданный результат, остановили таймер и исчезли из очереди. Остальные задачи
не завершались и не удалялись.

Очередь, связанные задачи, фильтры, запуск и переключение через карточку,

Контроль первоначальной истории показал итог 315 секунд. Он равен 127 секундам
предыдущих работ, 151 секунде проверенных новых непаузных интервалов и 26+11
секундам проверки восстановления. Паузы 32 и 22 секунды исключены.

Во втором аккаунте `rkrsviberlink`, сделка `32745819`, новая сборка загрузила

не затронула длительную активность первого аккаунта. История второго показала

На сделке, списке контактов, карточке контакта и экране задач наблюдалась одна

## Отказы и восстановление

Точечная блокировка state-чтения показала доступное сообщение об ошибке.
После удаления правила Refresh восстановил данные без перезагрузки.
При такой же блокировке дольше минуты во время работы таймер продолжал идти,
Stop оставался доступен. Восстановление не сбросило время.

Клиентская блокировка sessions-write показала «Восстановить операцию».
Снятие правила и повтор создали один интервал; явный Stop закрыл его.
Это блокировка до отправки, а не потеря ответа после принятия сервером.
Повтор во втором аккаунте проверен через reload с незавершённой командой.
После перезагрузки новое действие оставалось заблокированным до явного
восстановления. Снятие правила, восстановление и Stop оставили ровно один
16-секундный интервал с исходным именем. Вместе с первым 30-секундным интервалом
итог второго аккаунта составил 46 секунд. Временные сетевые правила удалены.
Анонимные state, browser-session и management-panels запросы получили 401. Это не проверка обычной роли.

Во втором аккаунте исходный enrollment содержал только Никиту, 1/7.
Его временное исключение и reload скрыли idle-панель. При следующем reload
с cached-disabled и заблокированным первым state она показала ошибку и Refresh.
Снятие правила и повтор скрыли панель после принятого disabled. Исходный
состав 1/7 восстановлен с подтверждением «сохранено».

## Дефект общих настроек

В `rkrsviberlink` переход «Общие настройки аккаунта» открывает приложение,
но список панелей сообщает «Неожиданная ошибка интерфейса». Повтор воспроизводит
ошибку. DevTools без сетевых правил показывает GET `/api/v1/activity/panels`
со статусом 200 и телом `{"panels":null}`. Клиентский `listPanels()`
в `web-panel/src/settings/api.ts` вызывает `page.panels.map(fromManaged)`.
Аккаунт с существующей панелью загружается успешно. Пустое состояние не принято.
По исходникам вероятная граница расхождения находится в RPC-конвертации
`fromManagedPanelPage`: сервис нормализует пустой список в `[]`, а конвертер
создаёт структуру с nil-slice и не добавляет элементов для пустого RPC-ответа.
HTTP затем сериализует nil в null. Это вывод из кода; отдельный transport-тест
пустого ответа в этот прогон не добавлялся.

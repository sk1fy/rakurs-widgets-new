# Контроль задач 1.1.0 — установка MVP

Пакет не содержит секретов. Core и backend TeamOS должны быть развёрнуты до включения управляемого режима; настройка ключей, миграций, grants и proxy описана в `team-os-backend/docs/integrations/task-control-connection.md` и инструкции серверного релиза. Core должен иметь установленную интеграцию с product task-control и grant для компании/аккаунта. TeamOS должен уже знать amoCRM аккаунт.

## Сборка

```sh
TASK_CONTROL_CORE_ORIGIN=https://YOUR_CORE_HOST \
TASK_CONTROL_BACKEND_ORIGIN=https://YOUR_TEAM_OS_API_HOST \
sh scripts/build.sh
```

Подставьте публичные HTTPS origins, без `/api` и без завершающего пути. Адреса встраиваются только в архив, исходный `lib/deployment.js` остаётся пустым. Результат `../rkrs_lead_notasks.zip`, version 1.1.0. Сборка без адресов намеренно завершается ошибкой. Для автономного пакета явно задайте `TASK_CONTROL_STANDALONE_BUILD=1`. Такой пакет не предназначен для проверки интеграции.

## Подключение

1. Обновите архив существующей приватной интеграции amoCRM, сохранив её OAuth UUID. Не создавайте второй виджет поверх рабочего.
2. Откройте настройки виджета как администратор amoCRM. Флажок «Правила из TeamOS» пока выключен: опубликованные локальные правила продолжают работать.
3. Нажмите «Код подключения», скопируйте код в TeamOS → Интеграции → выбранный аккаунт → Контроль задач. Код одноразовый, 60 секунд, не передавайте его в логи и чаты.
4. В TeamOS сохраните и опубликуйте правила. Локальный каталог автоматически не импортируется; перенесите нужные правила явно.
5. В amoCRM нажмите «Код смены режима» и используйте его в TeamOS для активации managed. После этого включите «Правила из TeamOS» в настройках виджета и нажмите основную кнопку Сохранить. Перезагрузите вкладки amoCRM.
6. Проверьте менеджера из правила на сделке без незавершённых задач ответственного, затем создайте такую задачу и проверьте снятие ограничения. Проверьте отдельно другого менеджера, не включённого в правило.
7. Опубликуйте изменение в TeamOS: открытая вкладка получает его в течение 60 секунд. Бизнес-проверки и создание задач выполняются непосредственно в amoCRM.

## Поведение и ограничения MVP

Каждое подтверждение Core использует новый disposable JWT amoCRM. Backend TeamOS выдаёт короткую сессию; токены и коды не записываются в localStorage, cookie или console. Последние корректные правила хранятся только в памяти вкладки. При недоступности сервера существующая вкладка сохраняет их; после перезагрузки без связи managed не получает правил и не подменяет их локальными. Подтверждённый отзыв или удаление очищает правила после следующей проверки. Это клиентский контроль, мгновенная блокировка офлайн не обещается.

Публикация проверяется по аккаунту, подключению, эпохе режима, версии схемы, номеру версии и SHA-256. Локальные каталог и runtime_config не перезаписываются TeamOS. Для возврата сначала переведите подключение в standalone в TeamOS с новым кодом режима, затем снимите флажок в amoCRM, сохраните и перезагрузите вкладки. После отзыва подключения также явно выключите флажок для возврата к автономной конфигурации.

В MVP используются ручные одноразовые коды вместо окна обмена между сайтами; автоматический импорт локального каталога и расширенная диагностика отложены. Работа установленного пакета с реальным amoCRM проверяется владельцем после выкладки.

## Проверки разработки

`npm test` (65 тестов, включая 58 существующих), `npm run check`. Новые тесты проверяют одноразовые JWT, краткую сессию, отсутствие Core-запросов при каждом чтении, отказ между аккаунтами, отзыв, выход из managed, checksum, регрессию версий, outage и одновременное обновление.

# Контроль карточек без задач

Виджет amoCRM 1.1.0: автономный режим сохраняет правила в локальном каталоге и `runtime_config`; опциональный управляемый режим получает правила напрямую из backend TeamOS. Проверки карточек и работа с задачами выполняются в браузере amoCRM. [Установка MVP и сборка пакета](MVP-SETUP.md).

## Разработка интеграции с TeamOS

Рабочая папка виджета в этом репозитории — `rkrs_lead_notasks/`. Все дальнейшие изменения Контроля задач выполняются здесь.

За основу взят существующий виджет из `/Users/nikpeskov/Projects/sub-projects/leads_no_tasks/rkrs_lead_notasks`; исходная папка сохранена без изменений. На момент копирования версия — `1.0.29`. Версия `1.1.0` добавляет подключение TeamOS с явным включением; исходный автономный движок сохранён.

План интеграции: интерфейс правил в TeamOS, хранение и публикация в backend TeamOS, прямое получение конфигурации из backend TeamOS; amocrm-pro подтверждает установку и принимает техническую телеметрию. Существующий движок проверок и автономный режим сохраняются.

Архитектура зафиксирована в [ADR КТ-01.01](../../../amocrm-pro/docs/adr/0038-task-control-hybrid-integration.md)
соседнего репозитория Core ([копия в ClickUp](https://app.clickup.com/t/869fhtvty)).
Статус — согласовано 2026-10-15, редакция 3. ADR описывает два режима, одного владельца
изменений, явное переключение/откат и сохраняемое различие списка покупателей
и проверки их карточки. Управляемый режим пока не реализован.

Проверки из этой папки: `npm test`, `npm run check`. Сборка: `sh scripts/build.sh`; архив создаётся в корне репозитория как `rkrs_lead_notasks.zip`.

## Архитектура

- `script.js` — AMD composition root и lifecycle amoCRM.
- `lib/request_queue.js` — последовательная очередь 900 мс, GET dedupe, retry 429/5xx и cancel.
- `lib/amo_api.js` — same-origin transport к `/api/v4`.
- `lib/catalog_repository.js` — каталог, поля, элементы, batch restore по 50 правил.
- `lib/rules.js` — модель, serializer/validator и RuleEngine.
- `lib/snapshot.js` — канонизация, SHA-256, parse/compile runtime config.
- `lib/settings_controller.js` — draft/publish UI администратора.
- `lib/runtime.js` — context resolver, task checker, card guard и taskless list.
- `lib/task_assignment.js` — проверка исполнителя, предупреждение в форме и подтверждаемое создание задачи ответственному.

Обычный пользователь каталог не читает. Если у пользователя нет опубликованных правил, runtime не делает API-запросов. Проверка `/api/v4/tasks` выполняется по ответственному карточки и кешируется на 30 секунд. Учитываются только незавершённые задачи с совпадающими карточкой, типом сущности и ответственным. Просроченная незавершённая задача также считается наличием задачи.

## Задачи ответственного за сделку

Список сделок ограничен сделками текущего менеджера в настроенных этапах. Задачи других сотрудников не исключают сделку из списка. Проверка выхода из карточки ищет задачу её ответственного, в том числе при открытии карточки другим пользователем, если опубликованные правила распространяются на него. Флаг «Проверять ответственного» по-прежнему определяет, применяется ли правило только к ответственному менеджеру.

Штатная форма создания задачи в карточке (`.feed-compose_task`) по умолчанию получает ответственного сделки. При выборе другого исполнителя отображается предупреждение и кнопка создания отдельной задачи ответственному. В окне подтверждения можно проверить и изменить текст и срок. Перед POST виджет повторно проверяет ответственного и наличие его задачи. Двойное нажатие объединяется, POST создания задачи не повторяется автоматически после ошибки сервера. Исходная задача другого сотрудника остаётся в штатной форме и сохраняется её кнопкой «Поставить».

После изменений в контейнере задач кеш очищается. При возвращении к списку выполняется новая проверка; открытое окно обновляется каждые 30 секунд в активной вкладке. Изменение ответственного переключает проверку на нового менеджера. После создания отдельной задачи через API виджет обновляет свою проверку; штатная лента amoCRM может потребовать перезагрузки для отображения новой записи.

Подстановка и предупреждение работают в штатной форме создания задачи в карточке сделки. Массовое создание, мобильное приложение, сторонние интеграции и внешние API этим frontend-only виджетом не перехватываются; их задачи учитываются при следующей проверке. При ошибке проверки выход остаётся разрешённым с уведомлением.

## Draft и публикация

Сохранение правила сразу меняет элемент каталога. После этого контроллер записывает будущий snapshot в системный hidden input и вызывает `change`. Новая версия становится опубликованной только после основной кнопки «Сохранить» amoCRM. Если окно закрыто без неё, менеджеры продолжают использовать прежний snapshot; при следующем открытии settings будет показано расхождение hash.

## Установка и восстановление

Создаётся `_ПРАВИЛА_ЗАПРЕТ_СДЕЛОК_БЕЗ_ЗАДАЧ` типа `regular` и десять скрытых полей с кодами `RKRS_WT_*`. Сначала виджет запрашивает `is_deletable:false`; если конкретный аккаунт отвергает этот create-параметр, он перечитывает частично созданную схему, создаёт только отсутствующие CODE без спорного параметра и best-effort применяет защиту отдельным PATCH. Идентичность после установки определяется только `catalog_id`, field ID и CODE; переименование не влияет на работу.

Если каталог удалён, runtime менеджеров продолжает работать по snapshot. Администратор может восстановить новый каталог и правила; `rule_uid` сохраняются, `element_id` создаются заново. При лимите в 10 каталогов восстановление останавливается без удаления чужих списков.

## Обязательные spikes на dev-аккаунте

До production нужно подтвердить поведение внешней платформы, которое нельзя проверить unit-тестами:

1. Максимальный размер `runtime_config` на 10/50/100/200 правил и чтение non-admin через `get_settings()`.
2. Момент сериализации hidden input относительно Promise `onSave()` и остаётся ли settings modal открытой.
3. Batch-create каталожных полей с `code`, `is_visible:false`, `is_deletable:false` и select enum `0/1`; проверить, понадобился ли compatibility fallback.
4. Card model для `responsible_user_id`, актуальные task DOM selectors и событие после создания задачи.
5. Реальный DOM/state integration switch во время отключения (есть защита по `data`, install status и известным switch selectors, но контракт не документирует отдельный deactivate-флаг).
6. Поведение двух администраторов, одновременно редактирующих каталог (без backend действует last-write-wins).

## Ограничения v1

- Открытые вкладки получают новую ревизию только после полной перезагрузки amoCRM.
- При ошибке Tasks API guard работает fail-open и разрешает навигацию.
- Сделки загружаются по страницам по 250, максимум 100 страниц. Незавершённая выборка считается ошибкой проверки. Покупатели сохраняют прежнюю выборку первых 250 карточек.
- Задачи проверяются пачками по 50 карточек, максимум 10 страниц по 250 задач на пачку; незавершённая выборка считается ошибкой проверки.
- Физическое удаление catalog elements не используется; удаление правила выставляет `ARCHIVED=1`, `ENABLED=0`.


### Повторные напоминания (1.2.4)

При включённом «Показывать окно» список сделок без задачи ответственного
проверяется раз в 30 секунд в активной вкладке списка сделок/задач/покупателей.
Закрытие окна не отключает следующие напоминания. Если у ответственного появилась
активная задача, карточка исключается из следующей выборки. Чужая задача и
завершённая задача ответственного условие не закрывают; просроченная незавершённая
задача ответственного считается активной. Долгие выборки не запускаются параллельно.
На карточке «Запрещать выход» продолжает проверять каждую попытку навигации.

снова блокирует выход при незавершённой чужой задаче. После теста обе созданные
задачи завершены через штатный интерфейс, `is_completed=true` подтверждено API.
Рабочие задачи/ответственные не менялись. Этот smoke подтверждает правило владельца;
повторные напоминания1.2.4 требуют установки нового ZIP и отдельной живой проверки.

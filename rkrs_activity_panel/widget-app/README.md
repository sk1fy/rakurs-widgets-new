# MVP виджета сотрудников «Контроль активности 2.0»

Задача [КА-01.02](https://app.clickup.com/t/1amkccgcnzx).
Панель сотрудников написана на Vue; отдельная аналитическая React-панель
находится в `../web-panel/`. Обе используют amocrm-pro.

## Режимы

В amoCRM виджет проверяет наличие SDK `$authorizedAjax` и текущих account/user ID.
Каждый запрос получает свежий disposable token через SDK `$.ajax`, затем
отправляется в Core с `X-Auth-Token`. Кэш токенов `$authorizedAjax` не используется.
Без SDK или данных сотрудника отображается ошибка и действия недоступны.
Ошибка API не переключает виджет на локальные данные.

Симулятор включает демо явно: `__rkrsActivityPreview = true` в экземпляре
AMD-загрузчика → `context.mode = 'demo'`. Он использует отдельную локальную
модель, задачи и storage namespace `rkrs_activity_prototype_v1`.
Наличие DOM-слота симулятора само по себе не включает деморежим.

## Минимальные сценарии

- Своя очередь незавершённых задач amoCRM, выбор, старт и остановка таймера.
- Завершение задачи через форму результата; в live-режиме результат обязателен.
  Результат ограничен 2000 UTF-8 байт контрактом Core.
- Другая активность, пауза и базовый учёт открытого диалога Imbox.
- Текущая сессия и история читаются с сервера; одна активная сессия
  обеспечивается backend, время вычисляется по серверному timestamp.
- Повтор неопределённой команды сохраняет её UUID. При частичном успехе
  amoCRM/Activity показывается восстановление предыдущей операции.
- Отключение панели блокирует новые действия; ранее запущенный интервал
  можно остановить. Новые команды недоступны до загрузки состояния.
- Счётчик завершённых задач в live-режиме не показывается. Непустой результат
  сессии не является достоверным признаком завершения задачи.

Задачи, их CRM-контекст и завершение проходят через Gateway Core
`/api/v1/widget/activity/tasks`. Браузер не обращается к amoCRM API v4.
Gateway проверяет сотрудника, объединяет очередь между вкладками и управляет
бюджетом запросов amoCRM. Activity state/history/commands используют тот же
SDK-транспорт со свежим disposable token на каждый запрос.
Статические OAuth secrets и management credentials в сборку не включаются.
Общие настройки открываются через серверный browser-session; проверка
администратора остаётся на backend.

## Размещение в amoCRM

- Вид панели повторяет старый виджет: сценарий слева, сводка задачи с «Стоп»
  и выпадающей очередью, кнопка действия справа. Завершение задачи, пауза,
  история и настройки собраны в меню «⋯».
- В карточках задач действия добавляются в содержимое карточки: «Взять в работу»,
  «Переключиться на задачу», «Остановить задачу»; стили живут в
  `#rkrs-activity-layout`, потому что карточки находятся вне shadow root.
- Панель закреплена вверху `body` справа от навигации amoCRM. Глобальный
  стиль `#rkrs-activity-layout` сдвигает контейнеры страницы на фактическую
  высоту панели и снимается вместе с ней.
- Раз в секунду runtime проверяет, на месте ли панель, и возвращает её,
  если amoCRM перестроил страницу.
- На `/dashboard`, `/events/list`, `/stats`, `/amo-market` и `/settings`
  панель не показывается, как и в старом виджете.
- Сотрудник, не включённый в общие настройки, панель не видит, если у него
  нет открытого интервала или незавершённой операции. Последнее известное
  состояние хранится в localStorage, поэтому панель не мигает при загрузке.
  Ошибка первого запроса состояния или авторизации показывает панель с
  действием «Обновить данные», даже при сохранённом disabled.
- amoCRM вызывает `destroy` и `render` при каждой смене области. Контроллер
  после `destroy` ждёт 10 секунд и переиспользуется следующим `render`:
  данные и начатая команда не теряются при навигации.

## Запуск и сборка

Node.js 22.12+:

```sh
npm ci
npm test
npm run build:preview
# Отдельный порт, если React-панель уже занимает 5174:
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5176 --strictPort
```

`npm test` сначала собирает UMD, затем запускает модель, loader, runtime,
SDK-клиент и live-контроллер. После изменения виджета выполните
`npm run release`: симулятор загружает отдельный AMD/UMD-релиз,
поэтому одного HMR оболочки недостаточно.

Для реальной сборки задайте публичные HTTPS origins:

```sh
VITE_ACTIVITY_API_ORIGIN=https://api.example.invalid \
VITE_ACTIVITY_APP_ORIGIN=https://panel.example.invalid npm run release
```

API origin должен вести к Core; application origin — к React-панели
из allowlist Core. Это примеры, не адреса развёрнутого MVP.

`dist-remote/` содержит UMD с хешем и `release.json`; `dist-preview/` —
симулятор. Для ZIP загрузчика используется существующая команда:

```sh
npm run package:widget -- --assets-url https://assets.example.invalid/activity
```

Живой SDK-режим способен изменять задачи amoCRM. ZIP с адресом-заглушкой
не устанавливается в CRM. HTTPS-размещение, тестовый ZIP и установка
на согласованный тестовый аккаунт относятся к КА-01.04.
Порядок выпуска и отката — [mvp-release.md](../../docs/activity/mvp-release.md).

## Границы MVP

Локальные проверки транспорта и UI не подтверждают реальную установку SDK
или соответствие DOM текущей версии amoCRM. Проверка агентом на установленной
связке относится к КА-01.05, ручная приёмка пользователя — к КА-01.06.

DOM-хуки карточек, подтверждение штатного завершения через CRM, связанные
задачи и переиспользование контроллера уже реализованы. Автоматическая
проверка завершения объединяет одновременные чтения одного интервала,
не начинает чтение или новую stop-команду в скрытой вкладке.
Срок native intent остаётся 3 минуты, шаг повторной проверки 5 секунд.
Контроллер хранит подтверждённые CRM завершения в приватном Set по ID задачи.
Пропуск строки, неполная или stale очередь и фильтр будущих задач не стирают
подтверждение. Видимая строка полной non-stale очереди вызывает live detail-чтение.
Только ответ с тем же ID, владельцем и `is_completed === false` возвращает задачу
в работу. `fetched_at` описывает кэш и не доказывает повторное открытие.
Ошибки detail сохраняют подтверждение, следующий refresh повторяет проверку.
Скрытая вкладка не начинает такие чтения. Поздний ответ после команды или dispose
не меняет подтверждение. Чтение очереди не блокирует команды пользователя.
Эти данные живут до подтверждённого повторного открытия или dispose контроллера,
не сохраняются в browser storage и могут расти с числом завершённых им задач.
Горячие клавиши запуска и остановки отсутствуют. Отличия от старого
поведения Imbox и границы проверки нескольких вкладок перечислены в
[матрице MVP-01.05](../../docs/activity/mvp-01-05-acceptance.md).
Backend-проверка канонического CRM-контекста,
структурированные Imbox-поля и контракт достоверного счётчика завершений
также дорабатываются отдельно. Старые storage-ключи не мигрируются.
Журнал восстановления использует sessionStorage без credentials.
Если browser storage запрещён, повтор сохраняется только в памяти;
после перезагрузки восстанавливается текущая серверная сессия,
а сохранность локального intent не гарантируется. Полная политика
хранения и синхронизация вкладок относятся к КА-01.07.

Для проверки настоящего live-контроллера с SDK, который отвечает в памяти,
используйте [локальный fixture](fixtures/README.md). Он поддерживает ошибки
инициализации, повтор, native completion и удержание ответов. Этот fixture
не подтверждает авторизацию или DOM установленной версии amoCRM.

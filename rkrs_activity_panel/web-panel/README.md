# Контроль активности 2.0 — веб-панель

React 19 + TypeScript + Vite. Отдельное приложение: дневной экран, профиль
сотрудника, история задач и Imbox, оператор (план/факт), пропущенные звонки
и все настройки. Целевой backend — `amocrm-pro` (viewer API активности).
Дневной экран, «Неделя» и «Месяц» используют историю событий за 33 дня,
включая сегодня (контракт `period-v1`, см. ниже).

Текущий MVP и приёмка ведутся в
[ClickUp](https://app.clickup.com/t/1amkccgcnzu).
Исходные план и аудит переноса (контракты C1–C8, исправления
F1–F11): `amocrm-pro/docs/proposals/activity-v2-plan.md`,
`activity-v2-audit.md`.

## Запуск

```bash
npm ci
npm run dev:fixtures   # синтетика, http://127.0.0.1:5173/#/p/demo
npm run dev            # hybrid: нужен ACTIVITY_API_ORIGIN в .env, ссылка вида #/p/<view_key>
npm test               # unit-тесты формул и правил (vitest)
npm run lint && npm run typecheck
npm run build          # production, режим live
npm run e2e            # Playwright-путь; сначала запустить dev:fixtures (E2E_URL, E2E_OUT)
```

Состояния на синтетике: `?fixture=error|empty|partial|stale|slow` перед `#`;
для недели/месяца ещё `period-error` (503 расчёта периода) и `period-pending`
(дни «считается» и `refresh_after`).

## Просмотр пустых блоков профиля

В локальном dev-сервере (`live`/`hybrid`) можно явно включить примеры пустых
блоков профиля. Суммарное время, история задач и Imbox получают отдельный
помеченный пример полного дня, когда соответствующих сессий нет. Если нет
звонков, весь «Анализ событий» показывается отдельным тестовым примером,
без смешивания с реальными событиями. По умолчанию примеры выключены;
кнопка «Показать тестовые примеры» включает их с отдельной пометкой.
CRM-ссылки для этих примеров не создаются.
Production-сборка и режим `fixtures` этот fallback не включают.
Это средство просмотра интерфейса; оно не закрывает отсутствующие API.

## Режимы данных

| Режим | Что показывает |
| --- | --- |
| `live` (production по умолчанию) | Только amocrm-pro. События, справочники, проблемные списки и сессии — через viewer API. Для новых методов требуется обновлённый backend. |
| `hybrid` (dev по умолчанию) | Те же live API; dev-профиль отдельно может показать помеченные примеры пустых блоков. |
| `fixtures` | Всё синтетическое, жёлтый баннер. Не доказывает живую интеграцию. |

Подключено к amocrm-pro: `GET /api/v1/activity/view/panel`, `/view/timeline`,
`/view/employees/{id}`, `/view/events/{id}` (`Authorization: Bearer <view_key>`).
Ключ просмотра живёт только во фрагменте URL (`#/p/<key>`); в localStorage
пишется лишь хэш для ключа личных предпочтений. Факты звонка (C1) берутся из
`call_facts` некомпактной ленты/журнала: дополнительные карточки не нужны,
неизвестная длительность остаётся `null`, известный ноль — `0`. Обновление
backend реализовано локально; его наличие на сервере ещё нужно проверить.
Для старого backend: payload события, иначе карточки (≤ 150 за загрузку,
до 4 параллельно). Pending-факты не кешируются; готовые — на минуту.

Management API использует короткую браузерную сессию администратора,
выданную виджету (см. ниже). Для локального оператора также доступен
dev-proxy Vite: `ACTIVITY_MANAGEMENT_TOKEN`,
`ACTIVITY_INSTALLATION_ID`, `ACTIVITY_INTEGRATION_ID` в `.env` (без префикса
`VITE_`, в сборку не попадают). Без браузерного входа или явно настроенного
dev-proxy общие настройки недоступны; `hybrid` не заменяет их деморедактором.

## Неделя и месяц (period-v1)

Контракт — `amocrm-pro/docs/proposals/activity-period-v1.md` (решения R1–R10,
`DayStat` §3, правила периода §4, API §5, блоки §8).

Маршрут: `#/p/<key>?period=week|month&date=<любой день периода>`; без `date` —
текущий период, без `period` — дневной экран (`?date=` как раньше).
Переключатель «День / Неделя / Месяц» и стрелки двигают по периодам: назад —
пока последний день периода не раньше `history_from` (33 суток), вперёд — до
текущего. Выбор сотрудников и отделов, личное рабочее окно и фильтр воронок
панели — те же, что у дня; боковая панель показывает рейтинг периода.

Данные:
- `GET /view/period` (`kind`, `anchor`, `start_minutes`, `end_minutes`,
  `cutoff_unix`, `employee_ids`) — сотрудники пачками по 25. Первая пачка без
  `cutoff_unix` получает серверную отсечку, остальные запрашиваются с ней же.
  Ответ проверяется как у `/view/activity`: `formula_version = "period-v1"`,
  период/окно/отсечка повторяют запрос, все сотрудники на месте, `DayStat`
  целые; иначе ошибка «unavailable» без локального пересчёта.
- `GET /view/employees/{id}/period-days` (≤ 31 дня) — 2-минутные ленты для
  «Сравнения рабочих дней», грузятся при раскрытии сотрудника.
- Текущий период обновляется раз в `ACTIVE_REFRESH_MS` (90 с), дни `pending` —
  по `refresh_after`. Дни `partial` (бюджет сканирования backend) помечаются
  «неполные», `unavailable` — баннером о 33 днях истории; при
  `previous.available = false` — «нет прошлого периода».
- `fixtures` считают тот же `DayStat` из синтетических событий
  (`dayStatFromEvents`; рейтинг дня совпадает с `dashboard-v1`, тест паритета),
  `hybrid` ходит в live API.

Формулы блоков (`src/domain/formulas/period/`), Σ — по выбранным сотрудникам и
учтённым (`counted`) дням; прошлый период — «до той же точки» (§4):
- Итоги — `kpi[0]` исходящие звонки, `kpi[3]` закрытые задачи, `kpi[4]`
  смены этапа, `events`, `kpi[2]` письма, Σ`active`, Σ`idle_inside` (рост —
  плохо); дельта `(cur−prev)/prev`, оба 0 — «без изменений», prev 0 — +100 %;
  «прошло дней» — максимум учтённых дней среди сотрудников.
- По часам — среднее `min(1, active_h/elapsed_h)` по дням с `elapsed_h > 0`
  (режим «Звонки» — `call_h`), Δ сравнивает до той же точки прошлого периода. ▲/▼ отмечают
  лучший и худший часы с прошедшим временем, включая часы с нулевой активностью.
  Дельта рейтинга в п.п. считается к `previous.rating`.
- Сотрудники — Σ`active`, Σ`events`, рейтинг, % к прошлому; полоса от максимума.
- Динамика — `kpi[0]` и `kpi[3]` по дню; дни без данных — разрыв; прошлый
  период целиком — пунктир.
- Сравнение рабочих дней — по умолчанию прошедшие Пн–Пт; медианы первого и
  последнего события, разброс последнего, Σ активности и событий; повторяющиеся
  паузы — ≥ 8 отрезков подряд, пауза в ≥ max(2, ⌈0,6 × дней⌉) днях внутри их
  first..last.

Рейтинг периода = Σ`active` / Σ`elapsed` по учтённым дням (R1), проценты
округляются как у `dashboard-v1`.

## Структура

- `src/domain` — модели и формулы без React; каждая поверхность со своей
  формулой (процент dashboard, рейтинг профиля, анализ событий), без унификации.
- `src/api` — транспорт, ошибки amocrm-pro, адаптер viewer API, синтетика, hybrid.
- `src/settings` — переносимые модели и API настроек: личные предпочтения
  (localStorage), настройки панели (amocrm-pro + расширения C5), панель задач (C6).
- `src/features` — экраны: dashboard, period (неделя/месяц), employee, operator, missed, settings.
- `src/ui`, `src/styles` — примитивы и токены макета (только тёмная тема).

## Backend parity API (2026-10-26)

Viewer panel теперь содержит `crm_base_url`, `options` (воронки, операторы,
планы/пороги), `pipelines` и `task_panel_enabled`. `/view/problems` читает
последний полный фоновый CRM-срез; первый сбор ещё может быть не готов,
ошибки не подменяются нулевыми счётчиками. `/view/employees/{id}/sessions`
отдаёт Activity-owned интервалы задач/Imbox/пауз. `hybrid` эти два API больше
не заменяет fixtures. Тестовые примеры профиля остаются отдельным dev-only UI.

Управление из браузера открывается по ссылке, выданной
`POST /api/v1/widget/activity/browser-session` после fresh widget JWT и
проверки администратора. Credential находится только во fragment, немедленно
удаляется из URL и хранится в sessionStorage этой вкладки с ограничением 30 минут
(при недоступном хранилище — только в памяти). Перезагрузка сохраняет вход до
истечения срока; server-side expiry остаётся обязательным. После management 401
credential очищается, интерфейс предлагает повторный вход из виджета.
В localStorage credential не записывается. Management token не передаётся.
`#/settings/panels` и `#/settings/task-panel` — общие серверные настройки;
шестерёнка конкретной share-панели ведёт только в её личный вид.

Telegram отложен. MVP producer сессий находится в
[`../widget-app`](../widget-app/README.md), его live-ветка отделена от демо.
Наличие пустого списка сессий не означает, что новый ZIP уже установлен.

## Связка MVP с виджетом и общими настройками

Задача [КА-01.03](https://app.clickup.com/t/1amkccgcnzy).

- Настройки сотрудников, включения и порядка приоритетов сохраняются через
  существующий `/api/v1/activity/task-panel`. Последовательные сохранения
  используют подтверждённые ревизии; новый черновик не помечается сохранённым
  ответом от прежнего. Конфликт либо потеря прав блокируют редактирование
  до явной загрузки актуальных данных.
- Конфигурация панели, события сегодняшнего дня и сессии профиля/таймлайна
  обновляются каждые 90 секунд активной вкладки. Скрытая вкладка отменяет
  текущие чтения и не опрашивает источник; возврат сразу обновляет данные.
  Исторические события и интервалы не опрашиваются по таймеру.
- Ошибка фонового обновления сохраняет последние интервалы с пометкой.
  Смена источника, сотрудника, даты или часового пояса отделяет старый ответ.
  Отзыв доступа к панели скрывает ранее загруженный интерфейс.
- Отключение панели задач блокирует запуск новых интервалов, но записанная история
  остаётся доступна. Показ дополнительной полосы — отдельный локальный выбор.
- Профиль и полоса считают пересечение реального интервала с выбранным днём
  в часовом поясе аккаунта, включая полночь и DST. Открытый интервал растёт
  от серверного начала; паузы не прибавляются к рабочему времени.
  Завершение интервала не выдаётся за завершение задачи amoCRM.

`npm run e2e` собирает production React-приложение и проверяет вход из
настоящего UMD виджета на перехваченном API: admin/employee, память credential,
сохранение, CAS/потерю прав и применение настроек виджетом. Для этой проверки
предварительно установите зависимости `../widget-app` командой `npm ci`.
Отдельные harness проверяют visibility, 90 секунд, ошибки и поздние ответы
для профиля и дополнительной полосы. Полный путь также проходит desktop/mobile.

API браузерных проверок искусственный: реальные amoCRM/Core credentials
не используются. Размещение и ZIP на `amotehrkrs` — КА-01.04,
живая сквозная проверка — КА-01.05; локальные проверки её не заменяют.

## Приёмка дневного MVP

Актуальные границы, источники метрик и проверенные сценарии собраны в
[матрице MVP-01.06](docs/mvp-01-06-acceptance.md). Обновление текущих событий,
сессий и конфигурации выполняется через 90 секунд после завершения предыдущего
запроса в активной вкладке. Сбор проблемных списков сохраняет серверное расписание.
`node e2e/event-data-checks.mjs` проверяет production React и live-адаптер через
перехват HTTP. Это автоматическая проверка контракта, а не приёмка на реальном аккаунте.
